# 数据产物人工修复与修订发布 SOP

适用于能够通过“人工排障、重新构建候选产物、发布新修订”解决的问题；不替代安全事件、基础设施故障或需要修改消费者协议的专项流程。

## 1. 适用范围

本 SOP 面向数据流水线产物的问题，例如：

- 内容或摘要缺失、错误或与正文不一致；
- 图片导出、派生尺寸、索引或分片错误；
- 关卡、敌人、数值等上游格式变化导致的解析错误；
- 转换器、归一化逻辑或校验规则产生的错误结果。

它不要求所有问题使用同一种修复工具或发布格式。模块附录负责说明该产物的重建方法、依赖关系、验收方式和发布契约；主流程只规定共同的判断和证据。

## 2. 基本原则

1. **候选先于发布。** 所有修改先在独立工作目录中完成，发布对象必须是已经验收的候选产物。
2. **修订向前发布。** 已公开的 Release 和资产不可覆盖、删除或重新解释；修复使用新的修订身份，保留旧版本以便追溯和恢复。
3. **按依赖确定范围。** 记录直接修改的内容，也记录因此必须重建的下游产物。没有证据支持的全量重建不作为默认要求。
4. **验证问题与边界。** 验收要证明原问题消失、受影响依赖正常，并抽查未受影响的正常样本；抽查结果不得表述为全部内容的语义证明。
5. **证据优先于叙述。** 任务记录引用日志、manifest、哈希、测试结果和账本，而不是手抄结论。
6. **失败可恢复。** 发布状态不明时先查询远端状态再重试；调用可能重复计费时，不把重试描述为 exactly-once。
7. **修复应当干净而完整。** 优先修正根因和正式边界，避免只为当前样例添加补丁、特殊分支或旁路。代码、数据和测试都只做到证明行为所需的程度；不为了“覆盖率好看”或假设中的故障添加无证据的防御逻辑和测试。

## 3. 任务记录

每项修复维护一份记录，建议命名为 `repair-<short-name>-<date>.md`。至少包含：

| 字段 | 内容 |
| --- | --- |
| 问题 | 现象、首次发现时间、复现入口和影响用户/功能 |
| 范围 | 受影响的资产、键、版本、直接原因和已知下游依赖 |
| 基线 | 源版本、已有 Release/修订、代码提交、工具和配置版本 |
| 方案 | 修改内容、重建范围、模块附录、预计成本或耗时 |
| 验收 | 原问题、依赖、正常样本、双实现/客户端检查及通过标准 |
| 发布 | 修订号、候选 manifest、资产哈希、发布时间和发布人 |
| 消费确认 | 发现、下载、校验、激活和实际查询结果 |
| 证据 | 日志、账本 digest、测试输出、截图或外部记录链接 |

`pipeline_run_id`、CI run id 或同等执行标识应在任务开始时确定；没有的历史 `run_id` / `response_id` 继续标记为缺失，不补造。

## 4. 主流程

### 4.1 定位问题

1. 保存最小可复现输入、错误输出、源资产版本和当前产物身份。
2. 判断问题属于源数据、转换器、归一化、打包、发布还是消费者读取阶段。
3. 列出直接受影响的键或文件，并画出必要的下游依赖；不能确定的部分标为假设。
4. 若问题可能涉及安全、凭据泄露、数据删除或服务不可用，暂停本 SOP，转专项流程。

完成条件：任务记录能说明“什么错了、依据是什么、哪些内容可能受影响”。

### 4.2 制定修复方案

1. 选择可信基线和可信输入；必要时固定新的代码提交或转换器版本。
2. 明确是数据修正、代码修复后重建，还是二者结合。
3. 根据模块附录计算重建范围、预计调用/下载/构建成本和验收样本。
4. 只有在更换模型、供应商、关键参数或扩大范围时，才要求先做小规模试跑；配置未变且范围清晰的任务可直接构造候选。

完成条件：方案可以由另一位维护者复核，且不会把“修复当前产物”误当成“修复未来生成逻辑”。

### 4.3 构造候选

1. 从记录的基线创建独立工作目录，不在已发布目录上原地修改。
2. 只清理经确认失效的缓存、索引或中间产物；保留基线和删除前清单。
3. 执行模块附录中的重建步骤，记录实际生成、复用、跳过和失败的数量。
4. 生成候选 manifest 或等价清单，包含源身份、代码/工具版本、修订号、资产大小和哈希。
5. 对有外部调用的模块保存逐尝试账本；失败运行也保留账本和错误类别。

### 4.4 验收候选

验收至少覆盖以下三层：

- **原问题：** 能复现的错误不再出现；失效对象达到预期状态。
- **关联依赖：** 受影响的索引、派生文件、跨包关系和消费者接口正常。
- **边界抽查：** 少量未修改的正常对象仍保持预期，避免修复破坏共享路径。

结构、格式、数量、哈希和 manifest 检查原则上全量执行；语义、视觉或人工内容检查按模块附录规定抽样。涉及公共接口、数据选择逻辑或双实现时，扩大到双实现和对应的真实客户端检查。

候选验收失败时回到 4.2 或 4.3，不发布不完整候选。

### 4.5 打包与发布

1. 冻结已验收候选，重新记录最终资产哈希。
2. 确认发布身份符合模块契约：修订号递增、源版本正确、旧资产不覆盖，是否标记 Latest 由契约决定。
3. 先执行 dry-run 或等价的发布计划检查，再执行实际发布。
4. 保存远端 Release/资产 URL、响应和发布后的哈希；发布状态不明时先查询，不盲目重复创建。

当前数据包的约定是使用 `datarev-<versionId>-r<N>`，不覆盖旧 Release，也不把修订包标为 Latest。其他产物（例如图片分片）必须以自己的模块附录为准。

### 4.6 消费确认与收尾

1. 使用真实或生产式消费者确认发现、下载、manifest/哈希校验和原子激活。
2. 调用受影响工具，并检查一个正常样本；涉及多实现时至少验证每个实现的关键路径。
3. 确认服务健康、日志无持续错误，临时配置、测试服务和隧道均已清理。
4. 将结果、未验证范围、残余风险和后续任务写回任务记录；上传或归档账本并确认远端状态。

到这里才把任务标记为完成。历史计费、未保存的供应商响应或无法复现的语义质量，不得写成已验证事实。

## 5. 统一停止条件

遇到以下任一情况应暂停并保留现场：

- 修复范围扩大、成本明显增加或发布身份需要改变；
- 候选 manifest、资产哈希、源身份或修订顺序不一致；
- 关键调用返回超时/429/5xx，且无法确认供应商是否已处理；
- 发布成功与否无法从远端确认；
- 原问题消失但关联依赖或边界抽查失败；
- 发现需要删除历史资产、覆盖已有 Release、修改消费者协议或绕过校验。

暂停后先查账本、远端状态和本地证据，再决定重试、回滚候选或另开任务。新修订优先向前修复，不把普通回滚路径当作数据修复入口。

## 6. 模块附录模板

新增模块时复制以下结构，不修改主流程：

### 模块：<名称>

- **产物与身份：** 文件/Release/索引、版本和修订格式。
- **输入与基线：** 可信来源、基线选择、需要保留的历史内容。
- **依赖图：** 直接产物、派生产物、索引、跨包或跨实现依赖。
- **重建方法：** 可执行命令、人工步骤、是否支持增量和如何计算范围。
- **外部调用：** 供应商、重试、预算、账本及重复计费边界；无外部调用则明确写无。
- **结构验收：** 全量格式、数量、哈希、schema 和 manifest 检查。
- **内容验收：** 语义/视觉/数值抽查对象、样本选择和通过标准。
- **消费验收：** 哪些客户端、工具或服务必须实际验证。
- **发布契约：** 修订号、资产不可变性、Latest 规则、回滚/恢复方式。
- **已知限制：** 发现窗口、缓存、历史证据缺口和未实现能力。

## 7. 模块附录：需要修改 PRTS-MCP 本体

当数据修复暴露出 PRTS-MCP 的发现、校验、解析、渲染或兼容逻辑也需要修改时，先判断能否只发布数据修订。只有数据修订无法让现有消费者正确发现、激活或使用修复时，才把 PRTS-MCP 代码纳入本任务。

### 7.1 用户无感优先

优先选择不要求用户改配置、不要求重新配置 MCP、不改变默认输出、不改变工具名称或必填参数的实现。数据源切换、缓存恢复和兼容性处理应由服务端完成；需要用户手工迁移时，必须在方案阶段明确写出，并单独评估是否仍属于修复任务。

这不意味着隐藏实际行为变化。若结果排序、错误语义、缓存生命周期、网络请求或资源消耗发生用户可观察变化，应在变更说明和验收记录中说明，并增加相应的回归样本。

### 7.2 SemVer 判定

版本号按实际公共行为决定，不按改动量或文件数量决定：

| 变化 | 通常版本级别 | 示例 |
| --- | --- | --- |
| 修复错误结果、恢复既有数据发现/校验行为，工具面和配置契约不变 | Patch | 修订包发现顺序错误、缓存恢复错误、缺失 manifest 未被拒绝 |
| 增加可选能力，或需要用户主动采用的新配置/新工具，但保持既有调用有效 | Minor | 新的可选参数、新工具、新数据域 |
| 删除或重命名工具/参数、改变必填参数、破坏默认输出或部署协议 | Major | 需要客户端迁移的工具面或协议变更 |

“尽可能使用 Patch”是目标，不是为规避 Major/Minor 而重新定义公共行为的理由。只要现有客户端在相同输入下可能得到不兼容的结构、错误语义或调用方式，就按较高版本级别处理，并补充迁移说明。

### 7.3 分支、LTS 与发布路径

1. 先确认问题属于当前稳定线、`lts/1.7`，还是开发线；阅读 PRTS-MCP 的 LTS 政策和版本发布规则。
2. **LTS 的核心承诺是数据可用性。** 在 LTS EOL 之前，对应 LTS 版本必须持续获得可用的数据源更新。任何涉及 AKDP、投影仓库、发布标签、Release 发现或 PRTS 同步逻辑的修复，都必须证明不会切断这条数据链；不能因为现代 2.x 的修订机制已经可用，就让 1.7 停在旧数据上。
3. LTS 不是绝对不可修改，但修改必须严格局限于兼容性、数据同步、安全或关键缺陷范围，保持既有工具、参数、输出、传输和数据来源契约。必要时应在 `lts/1.7` 单独修复，并验证从源数据到 LTS 消费端的完整链路，再将适用修复同步到开发线。
4. 当前稳定 2.x 修复通常从 `main` 建 hotfix，发布后向 `develop` 前向同步；跨模块或非紧急改动仍按项目分支规则处理。
5. 代码发布需要同时检查 Python 和 TypeScript 实现、锁文件、CHANGELOG、版本文档、CI/CD、容器或 npm/PyPI 产物，以及正式服务升级方式。
6. 只有当代码修复已经进入消费者可用版本后，才把数据修订作为依赖该修复的发布对象；否则先发布代码，再发布数据修订并验证发现顺序。

对 LTS 数据链条的检查至少包括：源仓库仍可发布、投影或兼容 Release 仍会更新、LTS 客户端仍能发现并校验新资产、旧版本数据工具仍能读取修复后的产物。若无法证明兼容链路，先暂停发布，不用“现代客户端已经正常”代替 LTS 验收。

### 7.4 本模块的最低验收

- 两套实现的工具名称、必填参数、输出契约和错误边界没有非预期差异；若有意变化，已有迁移说明。
- 代码能发现正确的源版本/修订，拒绝错误 manifest、重复身份和不安全降级，并正确执行原子激活。
- 受影响的数据工具通过真实或生产式调用；至少覆盖修复对象、一个相关依赖和一个正常样本。
- 需要发布时，版本号、tag、包内容、容器/启动入口和生产服务握手版本一致。
- 生产升级后确认健康状态、自动同步周期、实际激活身份和旧客户端的预期兼容行为。

若代码改动只是为当前数据修订提供一次性旁路，除非有明确兼容性理由，不应合入公共实现；应在任务记录中说明为何没有采用临时旁路。

## 8. 当前模块附录的起点

- **摘要：** 使用候选树的增量摘要和全量 `validate`；章节变更可能使所属活动摘要变脏；外部 LLM 调用需试跑、预算和账本。摘要验收包括门禁、sidecar 一致性、受影响章节及活动工具结果。
- **图片：** 先核实图片 baseline、delta、派生尺寸和索引的实际发布契约，再补充本附录；不得直接假定数据包的 `datarev` 规则适用于图片。
- **关卡/数值：** 先核实 schema 版本、解析器、索引和跨域引用，再补充格式契约与代表性查询；格式变化可能需要代码修复后重建。

本 SOP 冻结通用决策框架。模块附录应在首次处理该类问题前补齐，并以实际命令、真实产物和可复现验收结果为依据。主文档规定阶段、判断和证据，不替代各模块自身的 schema、发布契约、兼容性政策或运维手册；这些契约发生变化时，应更新对应模块附录并重新审阅适用范围。
