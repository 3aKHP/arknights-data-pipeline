# 图片基线生命周期：2026「感谢庆典」窗口临时裁决

日期：2026-10-29（裁决日期；以合并记录标识公开生效时间）

状态：**冻结的临时裁决**。本文不替代 [`image-baseline-lifecycle-preliminary-memo.md`](image-baseline-lifecycle-preliminary-memo.md)（后者继续作为评估素材），在其第 5 节“当前临时边界”基础上作出本轮窗口的正式裁决，并登记实验轨道。完整生命周期冻结文档的承诺**顺延至下一候选窗口（2027 农历新年）前**；届时如本文与最终冻结文档冲突，以最终冻结文档为准。

## 1. 裁决

1. **2026「感谢庆典」窗口不执行 re-baseline。** 感谢庆典版本更新按普通 delta 发布，由现有 `akdp-images/v1` 基线（`images-baseline-26-08-03-23-34-20_a745fc`）与既有 delta 链承载。下游不需要任何客户端更新（prts-mcp `3.1.2` 可原样跨过本窗口）。
2. **首个 re-baseline 候选窗口顺延至 2027 年农历新年**（按备忘 §2.1 的口径：以目标限定寻访及其对应的首个正式客户端 `versionId` 为机器判定身份，公历日期仅为人类可读提示）。
3. **登记一条实验轨道**（第 4 节）：在结构隔离的前提下开展 re-baseline 全流程实弹演练，产物一律不进入生产权威；转正裁决留待下一候选窗口，凭实验证据决定。

本文件构成 README 原有“2026「感谢庆典」前瞻直播前冻结”承诺的首期交付：冻结本轮**不重切**的裁决与实验边界；完整生命周期 spec（备忘第 4 节九问的答案）随实验证据在下一窗口前形成。

**概念澄清（并纳入最终冻结文档）**：一年四个活动窗口是正式生命周期上线后的**运维节奏锚点**（人工可预期的操作窗口），不是 re-baseline 的**技术前置条件**——活动版本更新与平时的大型阶段性更新在数据形态上并无本质差别，re-baseline 不依赖活动日历，但仍须具备完整输入与已验证的构建、发布和激活流程。窗口锚点管的是“正式转正的节奏与审批”，实验不受其约束。

## 2. 裁决依据

- 备忘 §2.3：当前实现没有显式、可审计的 re-baseline 构建/候选/激活流程，发布器存在 `--clobber` 覆盖风险；备忘 §4 的构建、激活、迁移与保留策略尚未形成完整冻结答案。在此状态下强行重切，恰好暴露于其警示的全部失败模式。
- 备忘 §3.1 明确“候选窗口 ≠ 必须发布”，任何构建、完整性、兼容性或真实消费验收不满足时沿用上一 baseline 并正常发布 delta 属设计内兜底。
- 现有 baseline 的两个 original 分片分别为 1,801,151,651 和 1,831,760,104 字节（约 1.80 / 1.83 GB），占备忘所列 2 GiB 单文件上限的 83.87% 和 85.30%。现有 baseline 不随普通 delta 发布而增大；新 baseline 的分片体积与增长余量须由后续构建实测，不能由现有分片占用率推定。
- 周期性全量重下代价：`baselineVersion` 变化会使全部存量部署离开增量复用路径并重新下载（large+preview 约 1.50 GB；含 original 约 5.14 GB），存量代际免重下迁移（备忘 §3.4）尚未设计和验证——本轮没有必要为了对齐活动日历触发该代价。

## 3. 延续的临时边界

备忘 §5 的全部条款继续有效并延长至完整生命周期冻结文档产生：

1. 当前 `akdp-images/v1`、首个 baseline 与既有 delta 链继续作为生产权威；
2. 自动工作流只发布普通 delta，不自动发起 re-baseline；
3. 不以“四个活动窗口”作为现有代码已经承诺或已经实现的行为；
4. 不因基线生命周期工作修改 #4 的 PNG 编码策略，也不把格式迁移并入；
5. 不删除、覆盖或重写现有 baseline、delta、index 或 build-state Release 资产。

## 4. 实验轨道登记

### 4.1 正式交付与实验边界

消费端前置功能由 [prts-mcp #288](https://github.com/3aKHP/prts-mcp/issues/288) 交付：`PRTS_DATA_SOURCE_REPO=owner/repo` 统一指定数据与图片同步源，自定义源使用独立数据目录。按本期交付顺序，须完成 prts-mcp 3.1.3 正式发布及渠道验收后，再进入另行设计的实验阶段。`GITHUB_TOKEN` 与 `GITHUB_MIRRORS` 沿用已有语义；镜像是直连失败后的回退，不是强制仅走镜像的开关。

实验 Release 全部由独立仓库承载。工厂发布凭据只允许写入实验仓库，不具有生产仓库写权限；实验客户端使用独立数据目录并绑定实验源。仓库边界、凭据权限和本地目录隔离共同构成实验边界，单独设置源仓库不能保证生产资产不可写。生产定时工作流不感知实验，行为不变。

实验构建能力在独立实验分支开发，不随本裁决合入默认分支。实验设计与操作手册另行审定；本文登记目标与约束，不宣告具体操作步骤已验证。

### 4.2 实验目标与证据要求

1. **Build / Publish / Activate**：明确候选构建、独立校验和权威 index 激活的边界，记录产物摘要、字节数、耗时与失败点。候选先以 draft 状态上传；须验证目标客户端及凭据组合下的发现行为，不能把 draft 状态本身视为所有客户端均不可见的证明。
2. **可复现图片输入**：固定目标 `versionId`、资源清单、原始图片 AB、摘要及解包与编码工具版本。公开 `data-<versionId>` Release 是 JSON / SQLite 数据产物，不能用作图片 AB 的全量重建输入。是否能够恢复特定历史版本的完整图片输入，须在实验设计中先验证。
3. **sentinel 发现与激活语义**：裁决同版本重切时由哪个 Release 传递新的 `baselineVersion`，验证 tag 不冲突、排序、index 一致性及新旧客户端行为。现有图片客户端同版本会跳过 index 下载，不能假定只改变 baseline 资产就能通知存量客户端。
4. **H1 / H2 / H3**：比较全量重建树与旧 baseline 加 delta 累积树的逐文件字节一致性，量化跟上进度与滞后客户端的复用率、下载量与耗时。H1 分歧须先归因，不能据此直接认领和解前提成立。
5. **消费者矩阵**：覆盖 fresh install、存量跟上进度、滞后、混合舰队、后续正常 delta，以及旧 index、损坏或缺失资产的失败行为。现有 Rust 图片同步在版本回退时可能从 baseline 重建，并非统一拒绝降级；实验须区分已观察行为与待冻结的转正策略。
6. **容量与运维证据**：记录候选各分片字节数、发布服务限制及增长余量。庆典 delta 体积、生产链长与自然同步表现另作只读观察，不依赖实验产物。

### 4.3 实验不变量与非目标

- 每轮固定输入时点快照，不追赶上游对相同 `versionId` 的静默热更新；独立产出 build state，不与生产或其他链的增量状态混用。
- 候选验证未过不公开；实验公开产物也不得覆盖重写，重试与归档规则在操作手册中确定。
- 本轮不实施分片 schema 或图片格式迁移；若实测容量无法满足现有六分片方案，先停止该候选发布并重新评估，不以未经验证的余量假设继续执行。
- 发布签名由 [prts-mcp #287](https://github.com/3aKHP/prts-mcp/issues/287) 另线推进，属于转正门槛，不作为本期实验设计的交付内容。
- **即使实验全绿，也不提前进行生产转正激活**。sentinel 语义、混合舰队、旧链保留策略须先有冻结文档背书，激活裁决依第 6 节门槛在下一候选窗口作出。

## 5. 庆典周的运维注意事项

- 继续使用现有普通 delta 自动发布链路。容量、任务状态与消费端代际按运维流程观察，单次预检记录不作为持续健康保证。
- 关注 #21（上游同 `versionId` 静默热更新无检测）：大版本后官方热修频率高，庆典周应关注数据异常，发现问题时按[手动修复发布 SOP](manual-repair-publication-sop.md)处理。
